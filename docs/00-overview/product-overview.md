## Purpose

Explain what MKO Data Cleaner is for, who uses it, and what it is intended to
become. This document focuses on the product: the problem, the users, the main
scenarios, the owner-confirmed intent, and the questions that are still open.
For implementation details see [current-behavior.md](current-behavior.md),
[data-flow.md](data-flow.md) and [architecture.md](architecture.md).

## What the Product Is

MKO Data Cleaner (`mko_data_cleaner`) is a local, pip-installable command-line
and Python tool that **post-processes Mediascope TV advertising exports** (the
TV / TV_REG reports) after they have been downloaded from Mediascope.

In plain terms, it answers three questions for a media analyst:

1. **"Which of these rows are junk?"** — rows the analyst no longer wants are
   deleted by rule.
2. **"What does this messy value mean?"** — raw advertiser/brand/category
   strings are recognized by a user-maintained dictionary and enriched with
   clean, analyst-defined columns (for example `BRAND CLEANED`, macro
   categories, marketplace flags, sponsor tags).
3. **"What did we fail to recognize?"** — rows that no rule recognized are
   exported separately so the dictionary can be improved iteratively.

The tool is deliberately **not** connected to Mediascope: it starts from a
folder of already-exported CSV files on disk. All processing happens locally
through a temporary SQLite database; nothing is uploaded anywhere
([confirmed by code](../../src/mko_data_cleaner/core/app_service.py)).

## The Problem It Solves

Mediascope exports use inconsistent, upper-case, company-specific naming
(hundreds of advertiser and brand spellings, retailer vs. manufacturer
variants, Cyrillic headers in some exports). Analysts need consistent
categories to build reports, but the exports are too large to clean by hand
and too repetitive to justify manual work every month.

MKO Data Cleaner turns the recurring cleanup into a **repeatable, rule-driven
pass**:

- the analyst maintains a dictionary CSV of search patterns and desired
  outputs;
- each month the cleaned report is regenerated by re-running the tool over the
  new export;
- rows the dictionary does not yet recognize are collected for dictionary
  improvement ("дообучение словаря", [README §Рекомендации](../../README.md)).

## Who Uses It

| Audience | Goal | Current usage |
|---|---|---|
| Media / data analyst | Turn a raw Mediascope export into a cleaned dataset with analyst-defined columns | CLI (`mko-data-cleaner run`) or Python (`process_data`) |
| Data-pipeline owner | Use the cleaning step as one stage of a Jupyter Notebook pipeline | **Target usage** (owner-confirmed, see below) — public library API |

The product owner is the sole maintainer today
([assumption A3](../../.ai/problems/01_pip_installable_jupyter_pipeline_step_spec.md)).

## Core Concepts

| Concept | Meaning | Where defined |
|---|---|---|
| Report directory | The folder passed to `run` / `process_data`; contains the input and receives the output | [current-behavior.md](current-behavior.md) |
| Raw data | CSV (optionally `.gz`) files in the report's `raw_data/` folder | [WorkingPaths](../../src/mko_data_cleaner/core/models.py) |
| Dictionary | User-maintained CSV of rules (`merged_dictionary.csv`); column positions are configured in `app_config.yaml` | [dict_service.py](../../src/mko_data_cleaner/core/dict_service.py) |
| Rule | One dictionary row: an action (`a`/`r`/`d`), a match type, a search column, a term, and the values to write | [ActionType / MatchType](../../src/mko_data_cleaner/core/models.py) |
| Extra column | Analyst-defined output column declared by the dictionary (e.g. `BRAND CLEANED`) | [dict_service.py `_initialize_mapping`](../../src/mko_data_cleaner/core/dict_service.py) |
| Clean data | Exported result table (all source columns + extra columns) in `clean_data/` | [export_sql_to_csv](../../src/mko_data_cleaner/core/csv_service.py) |
| Non-mapped ("null") data | Distinct combinations of search/extra columns where any extra column stayed empty; **dictionary-improvement feedback only** — not a data-quality report or error signal (owner decision D14) | [build_non_mapped](../../src/mko_data_cleaner/core/db_service.py) |
| User settings directory | Per-user folder with `app_config.yaml` + `log_config.yaml`, created by `init` / `initialize_settings()` | [paths.py](../../src/mko_data_cleaner/core/paths.py) |

## Main Scenarios (as implemented today)

1. **First-time setup** — run `mko-data-cleaner init` (or
   `initialize_settings()`): copies the packaged YAML templates into the
   per-user settings directory.
2. **Prepare a report folder** — place raw export files in `raw_data/` and the
   dictionary in `dict/merged_dictionary.csv` (paths are configurable).
3. **Run the cleaning pass** — `mko-data-cleaner run <report_dir>` or
   `process_data("<report_dir>")`: rules are applied in the fixed order
   DELETE → REPLACE → ADD; results land in `clean_data/`, unrecognized
   combinations in `null_data_*.csv.gz`.
4. **Iterate the dictionary** — inspect `null_data_*`, add rules, re-run.

Each scenario is traced with evidence in
[current-behavior.md](current-behavior.md).

## Target Product Behavior (owner-confirmed)

The owner's business goal is to use this tool as **one cleaning step inside a
Jupyter Notebook pipeline, installed via pip**. The requirements, decisions and
constraints were investigated and confirmed with the product owner on
2026-10-14 and are recorded in
[`01_pip_installable_jupyter_pipeline_step_spec.md`](../../.ai/problems/01_pip_installable_jupyter_pipeline_step_spec.md)
(decisions **D1–D11**, requirements **R1–R10**). Highlights:

| # | Confirmed intent |
|---|---|
| R4/D3/D7 | Public API is exactly two functions — `initialize_settings()` and `process_data(report_dir)` (directory input) — plus an optional `settings_dir` parameter; `core/*` stays internal |
| D2/R3 | Missing settings produce a dedicated, self-remediating error (`SettingsNotInitializedError`, catches as `FileNotFoundError`); no silent auto-writes |
| D8/R5 | `process_data` returns a structured result (paths + timings + clean row counts); not per-rule statistics |
| D9/R7 | A ready-to-run example notebook with a tiny synthetic sample (no 43 MB file) |
| D10/R8 | CI builds and verifies the wheel/sdist, fresh-venv install + import smoke |
| D1/D11/R6 | First release `0.1.0`, installed from a pinned git tag; PyPI later |
| D4 | License is BSD-3-Clause with the author's copyright line (SPDX form) |
| D5 | `list_settings` is repointed to the user settings directory (not removed) |
| D6 | No compatibility shim for the old internal import path |

**Status at the time of writing** (see
[open-questions.md](open-questions.md) for the gap register):

- Done: import-time crash fix (R1), YAML templates shipped in wheel/sdist
  (R2), dedicated missing-settings error (D2), English strings in the new CLI
  messages, `list_settings` repointed (D5).
- Not done: top-level package re-exports (`__init__.py` is empty), the result
  object (owner decision D8, tracked as gap D-6), `rich` declared, SPDX
  license + corrected copyright, `__version__`, example notebook (D9), CI
  (D10), `v0.1.0` tag (D11).

The processing pipeline itself (CSV → Polars → SQLite → rules → export) is
considered functionally adequate and is **not** part of the rework
([owner/auditor-aligned assumption A1](../../.ai/problems/01_pip_installable_jupyter_pipeline_step_spec.md)).

## Constraints and Non-Goals

Explicitly out of scope for the product
([spec §11](../../.ai/problems/01_pip_installable_jupyter_pipeline_step_spec.md)):

- rewriting or optimizing the cleaning/ETL logic or the SQLite usage;
- orchestrator adapters (Airflow/Prefect), Docker images, plugin system;
- switching the build backend; GUI or web surfaces;
- automatic publishing to PyPI (later phase, D1);
- the future of the 43 MB tracked sample (kept as-is for manual runs).

## Success Criteria (product level)

1. From a clean environment, `pip install` from the pinned tag, then a notebook
   can run `initialize_settings()` → `process_data(report_dir)` and read
   `clean_data/` (R1, R7, R10).
2. Running without initialized settings fails with the dedicated error that
   names the remediation (R3, D2).
3. The pipeline step returns result paths + row counts so the next notebook
   cell depends on the result, not on guessed file locations (R5, D8).
4. Missing settings, missing input files and invalid input are reported as
   understandable errors, not import-time crashes (R1).

## Unresolved Product Questions

Several product-level questions cannot be answered from the repository and
are recorded, prioritized, in [open-questions.md](open-questions.md). The most
consequential ones concern the meaning of the dictionary column that the
default configuration silently ignores, whether `a` (ADD) should append to an
existing value or replace it (implementation overwrites), and the intended
scope of the non-mapped (`null_data`) output. No target behavior for these
topics has been assumed.
