## 2. Что я бы исправил в текущем проекте

### Проблема № 1. Импорт зависит от предварительно созданной конфигурации

В `src/mko_data_cleaner/app.py` на верхнем уровне импортируется `app_service`.

При этом в `core/app_service.py` есть глобальная инициализация:

```
app_service = AppService(    app_paths=APP_PATHS,    resolver=PathResolver(APP_PATHS.user_dir),)logging.config.dictConfig(app_service.log_config.model_dump())
```

А конструктор `AppService` при создании сразу вызывает подготовку логирования. Для этого он читает пользовательский `log_config.yaml`.

Получается последовательность:

1. Пользователь устанавливает пакет.
2. Пользователь импортирует `process_data` или запускает CLI.
3. Python создаёт `app_service`.
4. Сервис пытается прочитать пользовательскую конфигурацию, которой ещё нет.
5. Импорт может завершиться ошибкой до вызова `initialize_settings()` или команды `init`.

Проблема усиливается тем, что `yaml_to_dict()` при отсутствии файла возвращает `None`, а конструктор пытается передать результат в `LoggingSettings`. Это риск сбоя именно на первом запуске.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub

Что сделать: убрать создание `app_service` и настройку глобального логирования при импорте модуля.

Вместо глобального экземпляра использовать функцию-фабрику, которая создаёт сервис тогда, когда настройки уже доступны:

```
def create_app_service():    # Создать AppService после проверки настроек    ...
```

Далее:

- команда `init` должна работать независимо от существования пользовательских настроек;
- команда `run` должна получать сервис через фабрику;
- `process_data()` должен выдавать понятную ошибку, если настройки не инициализированы, либо безопасно инициализировать конфигурацию, если это выбранное поведение API;
- настройка логирования должна выполняться при запуске обработки, а не просто при импорте библиотеки.

Это небольшое изменение существующего кода, а не необходимость переписывать архитектуру.

### Проблема № 2. Шаблоны YAML могут не попасть в устанавливаемый пакет

Твои шаблоны находятся здесь:

```
src/
└── mko_data_cleaner/
    ├── settings/
    │   ├── app_config.yaml
    │   └── log_config.yaml
    ├── core/
    └── app.py
```

Код `init_service.py` копирует файлы из `APP_PATHS.app_settings_dir`, то есть из `settings` внутри пакета, в пользовательскую директорию конфигурации.

Но в существующем `MANIFEST.in` есть правило:

```
recursive-include mko_get_mediascope_data *.json *.yaml
```

Оно ссылается на прежнее имя пакета, а не на `src/mko_data_cleaner/settings`. В текущей конфигурации нет отдельного правила, которое явно включает YAML-шаблоны в дистрибутив. Поэтому после установки пакет может потерять необходимые файлы настроек. Setuptools требует явно включать такие ресурсы через подходящую конфигурацию данных пакета или `MANIFEST.in`.&#x20;

[tool.setuptools.package-data]
mko_data_cleaner = ["settings/*.yaml"]

Важная проверка: после изменения нужно собрать wheel и убедиться, что в нём действительно присутствуют оба YAML-файла. Я изучал опубликованный код, но не запускал сборку репозитория в отдельном окружении, поэтому фактическое содержимое готового wheel ещё нужно проверить.

## 3. Как правильно организовать такой pet MVP

Я бы разделил задачу на три понятные части: библиотека, настройки и способ установки.

### Принцип 1. Ядро должно работать независимо от Notebook

Не нужно создавать специальную интеграцию с Jupyter, Airflow или другими инструментами, чтобы использовать проект как шаг пайплайна.

Notebook должен просто вызывать обычную Python-функцию. У тебя уже есть подходящий интерфейс для этого. Судя по README и реализации, сейчас он рассчитан на каталог отчёта с файлами и настройки обработки, а не на DataFrame, передаваемый в функцию. Для потоковой очистки CSV это вполне разумный первый вариант.&#x20;

### Принцип 2. Один стабильный публичный API

Для MVP достаточно двух публичных операций:

```
initialize_settings()process_data(report_path)
```

Первая подготавливает настройки, вторая запускает обработку.

Пользователям не следует рекомендовать импортировать:

```
from mko_data_cleaner.core.app_service import app_service
```

Это внутренняя реализация. При изменении классов, структуры модулей или инициализации она может сломать чужие Notebook. Лучше оставить `core` внутренним, а внешний API поддерживать стабильным.

В дальнейшем полезно, чтобы `process_data()` возвращала путь к каталогу с результатами либо небольшой объект с итогами обработки. Тогда следующий шаг пайплайна будет зависеть от результата предыдущего шага, а не от предположений о расположении файлов. Но для первого MVP это не обязательная крупная переработка.

### Принцип 3. Конфигурация должна быть предсказуемой

Сейчас `platformdirs` используется для пользовательской директории конфигурации, а пути данных и словаря задаются в `app_config.yaml`. Для твоего текущего способа работы это допустимо.

Однако в документации нужно чётко объяснить, что `initialize_settings()` создаёт пользовательские настройки в системной директории конфигурации, а не в директории проекта Notebook. Кроме того, в примере использования нужно указать ожидаемое содержимое каталога отчёта, например `raw_data/` и `dict/merged_dictionary.csv`.

На первом этапе я бы не внедрял сложную иерархию конфигураций. Достаточно текущего YAML-подхода и проверки его корректности.

### Принцип 4. Не менять стек сборки без причины

У тебя уже есть `pyproject.toml`, `setuptools` и `src`-layout. По современному руководству PyPA, файл `pyproject.toml` описывает метаданные и способ сборки проекта, а стандартный процесс распространения включает создание source distribution и wheel.&#x20;

Зафиксировать внешний API

Собрать wheel и sdist командой `python -m build`, установить wheel в новое виртуальное окружение и проверить, что доступны CLI, настройки и основная функция. Добавить простой GitHub Actions workflow, который запускает тесты и сборку при push и pull request.

## Итоговая рекомендация

Начни с этапов 1 и 2 — исправления инициализации и упаковки ресурсов. Это не косметические улучшения: сейчас именно они могут помешать установке и первому запуску в другом окружении.

Так ты решишь основную задачу без ненужного усложнения: проект останется самостоятельным инструментом очистки данных, но станет полноценной устанавливаемой зависимостью для Jupyter pipeline.
